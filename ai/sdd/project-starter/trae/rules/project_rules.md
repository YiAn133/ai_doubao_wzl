## 3. 项目目录结构规范

```
【项目名】/
├── src/                    # 源码
│   ├── 【入口A】/
│   ├── 【入口B】/
│   ├── services/           # 业务服务（调用第三方、存储等）
│   └── shared/             # 共享类型、常量、消息协议
├── docs/                   # 文档（proposal、design、layouts、tasks）
├── 【规则目录】/rules/       # 项目规则（本文件）
├── package.json
└── 【构建配置】
```

- 各入口文件职责单一，不得互相引用 UI 层细节。
- 跨模块共享代码统一放入 `shared/` 或 `services/`，避免重复定义。

## 4. 依赖管理规范

- 包管理器：【npm / pnpm / yarn】。
- 只引入实现当前任务必需的依赖；新增依赖前需说明用途。

## 5. 代码风格规范

- 静态检查/格式化：【ESLint / Prettier 等】。
- 统一缩进、分号、引号风格。
- 禁止使用 `any`，公共接口与消息结构必须有明确类型。
- 共享类型收敛到 `src/shared/types.ts`。

## 6. 命名规范

- 文件与目录：kebab-case（组件文件 PascalCase）。
- 变量/函数：camelCase；组件/类：PascalCase；常量：UPPER_SNAKE_CASE；接口不加 `I` 前缀。

## 7. 组件规范

- 优先函数组件 + Hooks。
- 组件职责单一；展示与业务逻辑分离；自定义 Hooks 承载副作用与状态。
- Props 必须定义类型。
- 不在组件内直接操作存储或直接调用第三方，统一走 services 层。

## 8. 开发与文档规范

- **文档优先**：先有 proposal → design → layouts → tasks，再编码。
- **注释**：复杂逻辑加注释，说明"为什么"而非"做了什么"。
- **提交**：Conventional Commits（`feat: xxx` / `fix: xxx`）。
- **变更最小化**：只做任务要求改动，不做无关重构。

## 9. AI 助手任务执行规范（强制）

为确保开发过程有序可控，AI 助手必须严格遵循：

### 9.1 任务范围控制
- **严格按 `docs/tasks.md` 执行**，不得超出指定任务边界。
- **单一任务原则**：每次只执行一个明确任务，完成后等待用户确认再做下一步。
- **禁止自动扩展**：不得基于 design.md 自行扩展任务范围；如需扩展先征得用户确认。

### 9.2 任务指令格式
用户以下列句式下达任务（AI 应能识别并遵守）：
- 「请执行任务 X：[任务名称]」
- 「只完成任务 X，不要超出范围」
- 「完成后等待我确认再做下一步」

### 9.3 执行验收标准
- 每个任务完成后对照 `docs/tasks.md` 的验收要点自检。
- 检查所建文件是否都在任务范围内。
- 总结完成情况（产出文件 + 验证方式），等待用户确认。

### 9.4 异常处理
- 任务描述不清晰 → 先询问范围，不自行决定。
- 任务依赖未完成 → 明确指出依赖，等待用户指示。
- 发现超出范围的代码 → 主动询问是否需要清理。
